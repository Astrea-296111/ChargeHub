# 只读一致性门禁

`invariants.sql` 在一致性只读快照内执行，适用于已完成当前 V1–V7 迁移的数据库。每条 SELECT 都必须返回零行；迁移缺失、SQL 执行失败和任何非空结果均不能解释为通过。`check-invariants.py` 保存原始 TSV，并在发现违规时非零退出。

门禁核对的是已经保存的关系、计数、金额与状态，不把 `DIFF`、`REVIEW`、拒绝的渠道通知、异常计量原始证据或未解决对账项本身当作账务数据损坏。`CLOSED` 才要求现金净额等于正式应付、无退款预占及无未解决对账项。

退款预占只计入 INIT/PENDING/PROCESSING/UNKNOWN；FAILED_RETRYABLE 与 FAILED_FINAL 都不占原失败额度。前者重新预占后必须先进入 INIT 并增加 retry_attempt，后者不可重试。逐笔成功退款必须对应一笔相同业务号、渠道号、金额、币种、所属订单的 REFUND；非成功退款不允许已有 REFUND。聚合金额校验仍独立执行，防止不同业务号的错误互相抵消。

物理占用与财务审查分开核对。收到归属已验证的 STOPPED 后，连接器可在订单 REVIEW/等待补计量期间释放，安全的已结束用户也可开始下一单；这不等于原订单已出账或财务闭合。活跃绑定和并发占用校验因此排除具有 STOPPED、结束时间及 final_seq 的已结束会话，同时单独要求该会话存在相同设备、会话、连接器和结束序号的原始 STOPPED 证据。旧版本已结束会话没有 stop_confirmed_event_id 时仍按原始事件核对；新版本填有该字段时严格核对所指事件。原始 STOPPED 计量可在 REVIEW 中，门禁不会要求其计量争议已获批准后才认可物理结束。

财务操作与证据还校验租约状态、操作 attempt、批次/差异项归属和经验证响应是否存在。响应 JSON 在 MySQL 中会被规范化，不能直接对其数据库文本 SHA256 与接收端序列化哈希做比较；因此没有加入会误报的文本哈希断言。

该门禁不能替代签名校验、独立渠道查询、双向日账对账、计费规则测试或人工证据审批。对账金额冲突应保留为 DIFF；通过 UPDATE 改成匹配不是修复。
